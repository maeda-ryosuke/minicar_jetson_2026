# motor_speed: 速度 PI の実走解析

motor_driver の速度 PI（`speed_control: pi`）を実走 bag で評価するためのスクリプト。
ROS は不要で、PC の Python（numpy）だけで動く。

## 手順

1. **Jetson ホスト**：小さいトピックだけを抜き出して圧縮する

   ```bash
   cd ~/workspace/workspace_2026/minicar_jetson_2026
   python3 tools/bag_analysis/motor_speed/extract_small.py      # 一番新しい bag
   gzip -f ~/bag_small/*.db3
   ```

2. **PC**：コピーして展開する

   ```powershell
   scp jetson@172.20.10.9:~/bag_small/*.gz .\bags\small\
   ```

3. **PC**：デコードして解析する（作業ディレクトリに中間ファイルができる）

   ```bash
   python -X utf8 -I recover.py bags/small/<name>_0.db3 r_<name>.pkl   # SQLite のページを直接読む（途中で切れた bag も読める）
   python -X utf8 -I decode.py r_<name>.pkl d_<name>.npz                # CDR をデコードして npz に保存
   python -X utf8 -I dips.py <name>                                     # 止まりかけた場面を、地図上の位置つきで一覧にする
   python -X utf8 -I map_fit.py <name> 24 107 128 185                   # 通常走行区間で実際に必要だった出力（マップを引き直す材料）
   python -X utf8 -I count_speed.py <name>:24-107,128-185               # 出力カウントごとの定常速度（直線寄り / 舵大）
   python -X utf8 -I replay_map.py src/minicar_motor <name> 24-107      # 実走の指令を車両モデルに流してマップ候補を比べる
   ```

## /motor/speed_ctrl の列

`[v_cmd, v_meas, u_ff, u_p, u_i, u_out, state]`

state は次のいずれか。

| 値 | 意味 |
|---|---|
| 1 | PI 動作中 |
| 0 | 不使用（off、停止中、後退中） |
| -1 | /odom 途絶のため、マップの値だけで出力している |

## これまでの結果（2026-10-19）

| bag | 設定 | 実速/指令 | 実速が 0.35 m/s 未満の時間 |
|---|---|---|---|
| 202610162011_last ほか | オープンループ | 0.34〜0.38 | 24〜32% |
| 202610191124_speedpi | PI、ki 0.6、下限なし | 0.93（〜100 s） | 11% |
| 202610191200_speedpi2 | PI、ki 0.4、下限 0.25 | 1.00（通常区間） | 約 1% |

- 長い停止は、地図上の (-3.0, 3.4) 付近のコーナーでの壁への接触だった。舵いっぱいで 3 s 以上旋回した後、0.25 s で停止している。
- 必要な出力は 0.45〜0.85 m/s でほぼ一定（約 362 カウント）だった。マップは傾きが急すぎる。

## マップの引き直し（2026-10-20、机上）

コース上の定常速度（count_speed.py）:

| カウント | 364 | 363 | 362 | 361 | 360 |
|---|---|---|---|---|---|
| 直線寄り (<8°) | - | 0.61 | 0.66 | 0.69 | 0.90 m/s |
| 舵いっぱい (>=12°) | 0.49 | 0.47 | 0.49 | 0.51 | - |

- 揺れているとき、出力は約 10 カウント振れていた。そのうち 5〜6 カウントはマップ（u_ff）が MPPI の指令に合わせて動く分だった。
- 出力の内訳で一番揺れていたのは積分項（u_i）だった。急すぎるマップを積分が打ち消す「綱引き」になっている。
- マップを `367/364/361/356/352` カウント（v = 0.001/0.2/0.8/1.25/1.54）に引き直した。
- 実走の指令を再生するモデル（replay_map.py）で比べた結果:
  - 今のマップで、実機の数字（誤差 RMS 0.14 vs 実機 0.15）をほぼ再現できた。
  - 引き直したマップでは、速度の 2 s 振れ幅が 0.27→0.21、出力の振れが 6→4 カウントに減った。
  - 代わりに、段差からの再発進が 0.1 s 程度遅くなった（sim では 352 カウントが必要な段差で 0.52→0.64 s）。

## PWM の分解能（2026-10-20、机上）

- 結論：揺れの主因ではない。周波数を上げる必要はない。
- 1 カウントは 4.07 µs（60 Hz / 4096）で、コースの 0.6 m/s 付近では約 0.04 m/s（指令の約 6%）にあたる。揺れの振幅（約 10 カウント）よりずっと小さい。
- 周波数を上げると分解能は上がる。ただし PCA9685 は全チャンネルで周波数が共通なので、ステアのサーボも同じ周波数になる。アナログサーボで 60 Hz 超を使うのは危険で、pwm_params.json のカウントもすべて換算し直しになる。
- それでも必要になった場合は、ソフトだけで済む「カウントを周期ごとに交互に出して平均を中間値にする（ディザ）」方式が先の候補になる。
